# Настройка проекта через интервью

Результат — рабочая карта конкретного проекта, выбранные процессы и проверенный
пробный маршрут. Анкета помогает принять решения, которые нельзя узнать из файлов.
Она не требует разработки приложения и подключения сервисов.

## 1. Осмотр

Прочитай `AGENTS.md`, `PROJECT.md`, `project.json`, затем существующий README
и инструкции затронутых областей. Осмотри имена нужных папок без широкого чтения
архивов, секретов, зависимостей и медиа. Определи, это пустой каркас или действующий проект.

Не заменяй существующие правила шаблоном. Для действующего проекта подготовь
перечень точечных добавлений и сохрани исходники затрагиваемых инструкций
в игнорируемой папке `.local/backups/` до правки. Покажи изменения через diff.
Конфликтующие решения уточни; совместимые обратимые изменения выполни в рамках задачи.

## 2. Интервью

Используй [анкету](intake.md). Сначала заполни ответы, уже подтверждённые файлами
или текущим поручением, с указанием источников. Задавай по 2–3 недостающих вопроса.
Первый круг — цель, типовые задачи и признак готовности. Следующие круги нужны
только для решений, влияющих на маршрут. Предложи короткие варианты, где это полезно.

Пользователь может ответить свободным текстом или заполнить анкету целиком.
При неполном ответе продолжай независимую часть работы. Неоднозначность,
которая меняет область, публикацию или доступ, оставь открытой.
Пропущенное поле помечай «не определено». Молчание не считается согласием.
Не спрашивай ключи, пароли, платёжные данные и полный дамп рабочих переписок.
Для интеграции достаточно назначения, способа доступа и проверенного статуса.

## 3. Карта и процессы

Заполни `PROJECT.md` и `project.json` по подтверждённым ответам.
Пути разрешай от корня текущего репозитория, без домашних каталогов автора шаблона.

В `project.json`:
- `status`: `template` до настройки; `configured` после проверки карты;
- `name`, `purpose`, `audience`, `language`: контекст проекта;
- `areas`: только нужные области с уникальным `id`, путями `instruction`,
  `workflow` и массивом `checks` с командами или наблюдаемыми критериями;
- `sources`: список относительных путей к существующим источникам или URL;
- `checks`: общие команды проверки проекта, если они есть;
- `review.independent_for`: id областей, которым нужна независимая приёмка;
- `integrations`: объекты с `service`, `purpose`, `status`.
  Статусы: `not-connected`, `configured`, `verified`.
  Конфигурация сама по себе не подтверждает доступ.

Для каждой области сохрани правила рядом с работой, используя
`templates/area.md` как заготовку. Вложенный `AGENTS.md` и короткий
`CLAUDE.md` с импортом этого файла могут служить точками входа;
общую логику не дублируй. Не создавай отделы, роли, папки, реестры и навыки
для гипотетической работы.

Выбери подходящий процесс из `docs/workflows/` либо добавь один под реальные
повторяющиеся задачи. Проверь команды по существующему README и доступной среде.
Команда в JSON — описание; проверяющий скрипт её не запускает.

## 4. Пробная задача и сдача

Выбери один реальный безопасный пример из ответов. Пройди его маршрут от обычной
просьбы до локального результата и сохранения состояния. Пробная задача
не включает отправку людям, публикацию, push, деплой и подключение платных услуг
без отдельного соответствующего поручения.

Выполни `python -X utf8 scripts/check.py`, тесты из README и назначенные
проверки выбранной области. При недоступном Python назови этот этап невыполненным;
не устанавливай runtime без запроса. При обязательной независимой приёмке
используй другого агента; если его нет, оставь результат на проверке.

Установи `configured`, когда карта заполнена и её локальные ссылки/структура
проверены; доступ к интеграциям и приёмка пробной задачи фиксируются отдельно.
Если структурная проверка не выполнена, сохрани `template` и точный блокер.
Обнови `NOW.md` датой, результатом прогона, следующим шагом и вопросами.
Отдай пользователю карту изменений, итог пробной задачи и фактические ограничения.
