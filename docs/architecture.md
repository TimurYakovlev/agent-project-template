# Архитектура работы с агентом

Каркас хранит договорённости о работе рядом с материалами проекта. Благодаря этому короткий запрос может запускать целый процесс, а следующая сессия — продолжать с сохранённого состояния. Чтобы это стало полезно конкретному проекту, сначала нужно заполнить карту направлений, выбрать источники и определить признаки готового результата.

## Путь одной задачи

1. Агент читает общие правила, карту проекта и актуальную точку продолжения.
2. По смыслу запроса выбирает направление и его процесс. Короткая формулировка пользователя сохраняет все обязательные этапы этого процесса.
3. Читает первичные материалы задачи и определяет результат, границы, роли, проверку и способ передачи пользователю.
4. Выполняет работу. Существенные пробелы уточняет у пользователя; доступные независимые действия продолжает.
5. Проверяет фактический результат по требованиям задачи. Если процесс требует отдельного проверяющего, передаёт ему материал и критерии.
6. Передаёт результат с точным статусом и сохраняет состояние в `NOW.md`. Постоянные задачи обновляет по подтверждённым итогам.

Например, просьба «подготовь письмо о переносе доставки» ведёт к чтению условий и дат, подготовке текста и проверке. Наличие черновика ещё не означает согласование или отправку. Каждый из этих результатов агент подтверждает отдельно.

| Процессы | [task.md](workflows/task.md), [engineering.md](workflows/engineering.md), [content.md](workflows/content.md), [research.md](workflows/research.md) | Порядок работы для разных типов задач |

`PROJECT.md` помогает человеку и агенту понять устройство проекта. `project.json` хранит формальную карту: статус `template` или `configured`, список направлений с `id`, путём к инструкции, процессом и проверками. При настройке эти два файла должны описывать одно и то же.

`NOW.md` содержит краткую точку продолжения: выполненное, текущее состояние и следующий шаг. `work/tasks.json` хранит постоянные задачи. В обоих файлах нужны проверяемые факты; старый план сам по себе не подтверждает, что задача до сих пор открыта.

## Настройка под проект

В исходном состоянии статус проекта — `template`. Агент сначала изучает доступные материалы, затем задаёт недостающие вопросы по 2–3 за раз. Ответы без секретов он сохраняет в `docs/intake.md`, чтобы решения можно было проверить и уточнить.

Для каждого направления нужно определить:

- результат и адресата работы;
- источники фактов и местные инструкции;
- обязательные роли и проверки;
- доступные инструменты и границы внешних действий;
- способ передачи результата.

После этого агент заполняет карту, адаптирует процессы, запускает проверку каркаса и выполняет пробную задачу. Условия перехода к `configured` заданы в [процессе настройки](onboarding.md). Название статуса не доказывает работоспособность подключений: каждый необходимый доступ проверяют отдельно.

## Общая логика для двух агентов

`AGENTS.md` содержит общие договорённости. `CLAUDE.md` подключает его строкой `@AGENTS.md`. Навыки в `.agents/skills/` и `.claude/skills/` служат короткими входами в одни и те же документы:

| Навык | Общий процесс |
| --- | --- |
| `project-setup` | [docs/onboarding.md](onboarding.md) |
| `project-task` | [docs/workflows/task.md](workflows/task.md) |

Логику работы нужно менять в общих документах. Это сокращает риск расхождений между Codex и Claude Code. Форматы входов и ограничения облачных сессий описаны в [совместимости](compatibility.md).

## Роли и проверка результата

Исполнитель получает компактное задание: результат, аудиторию, источники, ограничения, принятые решения и критерии готовности. Он не должен восстанавливать их по всей истории переписки.

Проверяющий сопоставляет текущую версию с заданием и источниками. Когда нужна независимая проверка, её выполняет отдельный агент или человек. Смена названия роли в одном чате не создаёт независимости. При недоступности отдельного проверяющего агент фиксирует невыполненный этап и передаёт подготовленный результат с этим ограничением.

Технические проверки зависят от результата. Для кода это могут быть тесты и запуск нужного сценария, для текста — сверка утверждений и редактура, для публикации — проверка доступного адреса после разрешённого выпуска. Отчёт о проверке должен называть выполненные действия и их результаты.

## Границы автоматизации

Инструкции в Markdown описывают ожидаемую работу. Их соблюдение зависит от агента, его версии, доступного контекста и инструментов. Для обязательных технических ограничений проекту могут понадобиться отдельные проверки и настройки среды.

`scripts/check.py` проверяет структуру, локальные ссылки, JSON, входы навыков и простые сигнатуры секретов. Он не оценивает достоверность всех материалов, не подтверждает доступ к сервисам и не заменяет аудит безопасности. GitHub Actions запускает проверки только при наличии соответствующей возможности и настроек репозитория.

Каркас не устанавливает инструменты, не создаёт аккаунты и не получает ключи. Публикация, отправка сообщений, изменение внешних данных и развёртывание требуют разрешения в границах конкретной задачи. Пользовательский запрет или остановка имеют приоритет над ранее выданным разрешением.

## Расширение

Новое направление добавляют, когда для него появились собственные источники, правила или проверки. Для этого подходят [шаблон направления](../templates/area.md) и запись в `project.json`; карта в `PROJECT.md` должна остаться согласованной с ними.

Существующие инструкции меняют точечно. Перед переносом каркаса в работающий проект сохраняют исходные файлы и просматривают различия. Материалы другого проекта, его секреты и подключения в универсальный комплект не входят.
